# ADR-003: Data Deletion Strategy

## Status
Accepted

## Context
We needed to determine how to handle data deletion in our application to balance:
- Regulatory compliance (GDPR "right to be forgotten")
- Business intelligence requirements (historical reporting)
- Referential integrity in relational database
- User experience expectations (undo capabilities)
- Storage efficiency considerations

## Decision
We implemented a **soft delete** approach where:
- Instead of physically removing records, we set a `deletedAt` timestamp
- All queries automatically filter out soft-deleted records unless explicitly requested
- Hard deletes are only used for temporary/test data or when legally required
- We maintain referential integrity through foreign key constraints that respect the soft delete pattern

## Implementation
### Database Schema
```prisma
model Client {
  id            String   @id @default(uuid())
  name          String
  email         String
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
  deletedAt     DateTime?  // Soft delete field
  
  @@index([deletedAt])
  // Note: Foreign keys would typically reference only non-deleted records
}
```

### Query Layer
- Prisma middleware automatically adds `WHERE deletedAt IS NULL` to all find queries
- Special methods (`findDeleted`, `findUniqueWithDeleted`) available when needed
- Custom repositories encapsulate this logic for consistency

### Business Logic
- Delete operations set `deletedAt = new Date()`
- Restore operations set `deletedAt = null`
- Hard delete available via `deleteForever()` for special cases
- Export/reporting functions can opt-in to include deleted data

## Consequences

### Positive
- **Compliance**: Supports GDPR right to erasure while allowing audit trails
- **Data Safety**: Accidental deletes recoverable without backup restoration
- **Historical Integrity**: Preserves relational integrity for historical reporting
- **User Experience**: Enables "undo" functionality and recycle bin features
- **Performance**: No fragmentation from frequent deletes; indexes remain efficient
- **Legal**: Provides clear audit trail for data retention policies

### Negative
- **Storage Overhead**: Deleted records continue to consume space
- **Query Complexity**: All queries must consider the deleted state filter
- **Foreign Key Complications**: Requires careful handling of related records
- **Developer Cognitive Load**: Must remember which tables are soft-deletable
- **Index Efficiency**: Standard indexes on deleted columns may be less selective

## Alternatives Considered

### Hard Delete (Physical Removal)
- **Pros**:
  - Immediate space reclamation
  - Simpler queries (no deleted state filtering)
  - Straightforward foreign key relationships
- **Cons**:
  - No recovery from accidental deletion
  - Complex GDPR compliance (need to track what was deleted)
  - Breaks historical reports and audit trails
  - Requires complex archive/restore mechanisms
  - Higher risk of data loss

### Audit Table Approach
- **Pros**:
  - Complete history of all changes
  - Clean main tables (no deleted records)
  - Flexible querying of historical states
- **Cons**:
  - Significant complexity increase
  - Storage overhead (often 2-3x)
  - Query complexity for current state
  - Application logic becomes more complex

### Event Sourcing
- **Pros**:
  - Complete historical audit trail
  - Excellent for compliance and debugging
  - Enables temporal queries (state at any point in time)
- **Cons**:
  - Significant architectural complexity
  - Steep learning curve for development team
  - Overkill for standard CRUD applications
  - Query performance considerations for current state

## Implementation Notes
We implemented soft delete at the Prisma level using:
1. **Custom Prisma Client Extension** that automatically applies filters
2. **Database Indexes** on `deletedAt` columns for efficient filtering
3. **Repository Pattern** to encapsulate data access logic
4. **Migration Strategies** that handle existing data appropriately

## Boundary Conditions
- **Never Soft-Delete**: 
  - Authentication tokens (should be expired/removed)
  - Cache entries (transient by nature)
  - Temporary uploads (filesystem-based)
  - Logging/audit events (append-only)
  
- **Always Soft-Delete** (Business Entities):
  - Users, Customers, Clients
  - Bookings, Appointments
  - Financial Transactions
  - Inventory Items
  - Configuration Records

## Related Decisions

- Audit Logging: Complementary approach for tracking who/what/when

## Implications
- **Storage Planning**: Need to account for 5-20% overhead depending on churn rate
- **Backup Strategies**: Must consider that "deleted" data remains in backups
- **Performance Monitoring**: Query planners need to account for delete filters
- **GDPR Procedures**: Defined process for honoring erasure requests (may require hard delete in some jurisdictions)

## Compliance Note
For true GDPR "right to erasure" in certain jurisdictions, we may need to:
1. Immediately soft-delete (to stop processing)
2. Schedule hard-delete during off-hours (to actually remove from storage)
3. Maintain proof of deletion request and execution timestamp
