# ADR-002: Dependency Injection Container Pattern

## Status
Accepted

## Context
As our application grew in complexity, we needed to manage dependencies between services, controllers, and utilities effectively. We faced challenges with:
- Tight coupling between components
- Difficulty in unit testing due to hardcoded dependencies
- Inconsistent instantiation patterns across modules
- Challenges in managing singleton instances (database connections, service instances)

## Decision
We implemented a custom Dependency Injection (DI) Container pattern following these principles:
- Explicit registration of dependencies
- Singleton lifetime management by default
- Lazy initialization where appropriate
- Interface-based abstraction for testability
- Centralized bootstrap process

## Implementation
Our DI container consists of:
1. **Container Class** (`core/container/index.ts`): 
   - Registers dependencies with unique tokens
   - Resolves dependencies on demand
   - Manages singleton lifecycle
   
2. **Bootstrap Process** (`core/container/bootstrap.ts`):
   - Sequentially loads module bootstrappers
   - Ensures proper initialization order
   
3. **Module Bootstrappers** (`{module}.bootstrap.ts`):
   - Instantiate services and controllers
   - Register them in the container
   - Establish proper dependency relationships

## Consequences

### Positive
- **Testability**: Easy to mock dependencies in unit tests
- **Loose Coupling**: Components depend on abstractions, not concretions
- **Centralized Configuration**: Single place to review all dependencies
- **Lifecycle Management**: Consistent handling of singletons vs transient instances
- **Scalability**: Easy to add new components without modifying existing code
- **Debugging**: Clear visibility into dependency relationships

### Negative
- **Initial Complexity**: Slight learning curve for new developers
- **Boilerplate**: Requires registration code for each service
- **Runtime Errors**: Misconfiguration leads to runtime rather than compile-time errors
- **Overhead**: Minimal performance overhead for dependency resolution

## Alternatives Considered

### No DI Container (Manual Instantiation)
- **Pros**: 
  - Zero abstraction overhead
  - Explicit and obvious dependency flow
- **Cons**:
  - Tight coupling throughout codebase
  - Extremely difficult to test (requires integration tests for unit logic)
  - No centralized lifecycle management
  - Inconsistent patterns across team

### Third-party DI Containers (typedi, inversify)
- **Pros**:
  - Feature-rich (scopes, decorators, auto-injection)
  - Community support and documentation
- **Cons**:
  - Additional dependency weight
  - Learning curve for specific library
  - Decorator-based approaches can obscure implementation
  - Less transparent than explicit registry

### Singleton Pattern / Static Instances
- **Pros**:
  - Simple to implement
  - Global access without passing references
- **Cons**:
  - Nearly impossible to test properly (global state)
  - Hidden dependencies
  - Difficult to manage lifecycle (especially in serverless contexts)
  - Violates SOLID principles (particularly Dependency Inversion)

## Implementation Notes
We chose a custom implementation over third-party libraries because:
1. **Transparency**: Team understands exactly how dependencies are resolved
2. **Minimalism**: Only includes features we actually use
3. **Type Safety**: Full TypeScript support without relying on decorator metadata
4. **Flexibility**: Easy to adapt to specific needs (scoped instances, factories, etc.)

## Best Practices Established
1. **Interface Segregation**: Define minimal interfaces for dependencies
2. **Constructor Injection**: All dependencies received via constructor
3. **Singletons by Default**: Most services registered as singletons
4. **Explicit Scoping**: When needed, specify transient or scoped lifetimes
5. **Module Boundaries**: Each module responsible for its own bootstrapping

## Implications
- **Development**: Improved testability leads to higher code quality
- **Maintenance**: Clear dependency graph simplifies refactoring
- **Onboarding**: New developers can understand system boundaries quickly
- **Architecture**: Enables clean hexagonal/ports-and-adapters patterns
